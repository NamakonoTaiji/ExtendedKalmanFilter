# Stormworks マルチプレイにおける車載Luaの同期・非同期問題

作成日: 2026-08-11  
対象: Stormworks: Build and Rescue のマイクロコントローラー内Lua（Vehicle Lua）

## 1. 結論

Stormworksのマルチプレイでは、**車載Luaの変数・テーブル・実行途中の状態は、プレイヤー間で同期されない**。

そのため、次のような値をLua内部だけに保存すると、途中参加者や車両を新たに読み込んだクライアントでは初期値から始まる可能性がある。

- `counter = counter + 1` のような経過時間依存の値
- 最後に入力された目標座標
- レーダーの追跡履歴
- フィルターの内部状態
- ウェイポイントのテーブル
- モード切替や初期化済みフラグ

Geometaの不具合報告 #11067 に対して、開発者は **“vehicle Lua is not synced in MP”** と回答している。この問題は単なるコードミスではなく、基本的にはStormworksの仕様として扱う必要がある。

一方で、車両位置・物理挙動・コンポーネントの状態などにはゲーム本体のネットワーク同期が存在する。したがって、**「車両の物理状態が同期される」ことと「車載Luaの内部状態が同期される」ことは別問題**である。

## 2. 何が同期され、何が同期されないのか

| 対象 | 基本的な扱い | 注意点 |
| --- | --- | --- |
| 車両の位置・姿勢・物理挙動 | ゲーム本体がネットワーク同期 | 遅延や物理デシンクは別途発生し得る |
| スイッチ、キーパッド、ダイヤルなどのコンポーネント | 車両状態として同期され得る | 遅延、読み込み範囲、更新タイミングの影響を受ける |
| Luaのグローバル変数・ローカル変数 | 同期されない | 各Lua実行環境が独自の値を持つ |
| Luaテーブルの内容 | 同期されない | 座標履歴や追跡リストも同様 |
| `onTick`を何回通過したか | 同期されない | 途中参加者は参加後の実行回数しか持たない |
| Luaで描画するモニター表示 | 各クライアントのLua状態に依存 | 同じ車両でも異なる表示になり得る |
| Addon Luaの保存データ・マップUI | サーバー側で管理可能 | 任意の車載Lua変数を直接読み取れるわけではない |

この表の「同期され得る」は、Lua内部変数のように完全に各クライアント任せではない、という意味である。ネットワーク遅延や車両のロード状態まで含めて常に瞬時に一致することを保証するものではない。

## 3. 途中参加で何が起きるのか

次のコードを考える。

```lua
counter = 0

function onTick()
    counter = counter + 1
end
```

先に参加したプレイヤーAの環境で10,000 tick経過していても、後から参加したプレイヤーBのLuaは、その値を受け取って10,000から開始するわけではない。B側でLuaが新しく開始されれば、`counter`は0から増え始める。

したがって同じ時刻でも、例えば次の状態になり得る。

| 実行環境 | `counter` |
| --- | ---: |
| 先発参加者A | 10,000 |
| 後発参加者B | 60 |
| 再読み込みされた環境 | 0付近 |

重要なのは、問題が「`local`を付けたかどうか」ではないことである。ファイル先頭のグローバル変数でも、関数外の`local`変数でも、Lua VM内だけに存在する状態である限り同期用の保存場所にはならない。

## 4. 座標バッファで発生する問題

例えば次のコードは、入力された最後の非ゼロ座標をLua内に保存する。

```lua
local coordBuffer = {x = 0, y = 0, z = 0}

function onTick()
    local x = input.getNumber(1)
    local y = input.getNumber(2)
    local z = input.getNumber(3)

    if x ~= 0 or y ~= 0 or z ~= 0 then
        coordBuffer.x = x
        coordBuffer.y = y
        coordBuffer.z = z
    end

    output.setNumber(1, coordBuffer.x)
    output.setNumber(2, coordBuffer.y)
    output.setNumber(3, coordBuffer.z)
end
```

入力が現在も座標を出し続けているなら、新しく開始したLuaも同じ座標を読み取れる可能性が高い。しかし、入力が一瞬だけ座標を出し、その後0へ戻る設計では、後から参加したLuaは過去の入力イベントを知らない。その場合、先発側の`coordBuffer`には目標座標が残り、後発側では`{0, 0, 0}`のままになる。

また、`0`を「データなし」の印として使う設計には別の問題がある。世界座標では0が正当な座標になり得るため、次のように**有効フラグを別のBooleanチャンネルで渡す**方が安全である。

```lua
if input.getBool(1) then
    coordBuffer.x = input.getNumber(1)
    coordBuffer.y = input.getNumber(2)
    coordBuffer.z = input.getNumber(3)
end
```

## 5. ミサイルでは実害が出るのか

実害の有無は、「目標座標をどこに保持しているか」と「どの状態が実際の制御出力を決定しているか」による。

### 比較的問題が小さい構成

- キーパッド等が発射後も目標座標を保持している
- Luaが毎tick、現在の入力座標から誘導値を再計算する
- 過去のLua内部状態を使わなくても同じ制御結果を再構成できる

この場合、途中参加者のLuaが新しく始まっても、同期された入力から同じ状態へ近づきやすい。

### 問題が起きやすい構成

- 座標を1 tickだけ入力し、その後はLuaテーブルだけに保存する
- 発射時刻、積分値、前tickのLOS角、カルマンフィルター状態などに依存する
- 乱数、ローカルtick数、ロードされた時刻によって分岐する
- `onDraw`側でも状態を変更する

この場合、後発参加者のモニターには別の目標や誘導状態が表示される可能性がある。また、どの実行環境のロジック出力が実際の車両制御に影響するか、車両のロード状況やネットワーク状態まで含めて一律に決めつけるのは危険である。**「サーバー側では正しく飛ぶはず」と仮定して重要な誘導状態をLua内だけに置くのは避けるべき**である。

射手の意図した場所へ実際のミサイルが飛べばよく、後発参加者のモニター表示だけが異なることを許容できるなら、表示上の不一致は無視できる。ただし、誘導出力そのものに履歴依存の非同期値が入る場合は、見た目だけの問題とは限らない。

## 6. ループバックによる状態の復元

実用的な対策は、同期・復元したい状態をLua VMの外へ出し、Compositeなどを経由して入力へ戻すことである。

```text
Lua output → Composite Write → 車両ロジック → Composite Read → Lua input
```

Luaが新しく開始されたとき、最初の初期化処理でループバック値を読み込めば、過去の状態を再構成できる。Boolean値を戻すチャンネルが足りない場合は、複数のBooleanを1個の数値へビットパックする方法も使える。

ただし、ループバックは「すべてのLua変数を自動同期する仕組み」ではない。外へ出した値だけが対象であり、次の点に注意が必要である。

- 初期化時は、保存値を読む前に0を出力して上書きしない
- 有効フラグまたはバージョン番号を持たせる
- 0が正当な値になる項目に0 sentinelを使わない
- テーブルやフィルター状態は必要な要素をすべてチャンネル化する
- 一時的な入力と永続させる状態を分ける

座標なら、X・Y・Zに加えて「保存値あり」のBooleanをループバックする構成が扱いやすい。

## 7. `onTick`の差し替えを使った初期化

Discordで示された方法は、初期化後に`onTick`自身をメイン関数へ差し替えるものである。

```lua
function onTick()
    -- ここでループバック値を読み、状態を初期化する
    onTick = main
end

function main()
    -- 通常処理
end
```

この場合の動作は次の通りである。

1. 最初のtickで元の`onTick()`が実行される
2. 初期化処理を行い、`onTick = main`を代入する
3. そのtickでは、代入しただけで`main()`は自動実行されない
4. 次のtickからStormworksが`main()`を`onTick`として呼ぶ

つまり、初期化とメイン処理を同じtickで実行したい場合は、明示的に`main()`を呼ぶ必要がある。

```lua
function onTick()
    -- 初期化
    onTick = main
    main() -- 必要な場合だけ明示的に呼ぶ
end
```

一方、次の二段構成ではメイン開始は3 tick目になる。

```lua
function onTick()
    onTick = initialize
end

function initialize()
    counter = input.getNumber(32)
    onTick = main
end
```

- 1 tick目: `onTick = initialize`
- 2 tick目: `initialize()`で読込後、`onTick = main`
- 3 tick目: `main()`

この技法の利点は、毎tick `if initialized then ...` を評価せず、初期化処理と通常処理を明確に分けられることである。ただし、これは**同期処理そのものではない**。読み込むべき共有・ループバック値が存在して初めて意味を持つ。

## 8. 初期化後に新たな食い違いが起きる理由

ループバックで参加時点の値を揃えても、その後の各Lua実行環境は独立して動く。次の条件があれば再び差が広がる。

- tickの開始時点や実行回数が異なる
- あるクライアントだけ車両をロード／アンロードした
- 入力イベントを受け取ったタイミングが異なる
- 浮動小数点誤差を含む値を長時間積分する
- `math.random`等の乱数状態が異なる
- ローカルな表示・タッチ入力に基づいて状態を変更する
- 一方でだけLuaがリセット、タイムアウト、再初期化された

したがって、初期化は「その瞬間の状態を合わせる」対策であり、それ以降の全演算を永続的にロックステップ同期するものではない。同期が必要な値は、定期的に外部の正規状態から再取得するか、イベントが起きるたび外部へ確定値を書き戻す必要がある。

## 9. Dedicated Server、Keep Active、Addonの効果

### Dedicated Server

Dedicated Serverはホスト処理を分離し、検証条件を揃えるのに有効である。しかし、Dedicated Serverを使用しただけで車載Luaの変数が中央集約・同期されるわけではない。

### Keep Active

Keep Activeは車両がアンロードされてLuaが再初期化される機会を減らす用途では有効である。ただし、各クライアント間のLua変数を複製する機能ではない。また、Keep Active対象を増やすほどサーバーの物理・ロジック負荷が増えるため、過剰使用はマルチプレイ全体の遅延を悪化させる可能性がある。

### Addon Lua

Addon Luaを利用すると、サーバー管理の情報をマップマーカーとして全員へ表示したり、名前付きキーパッドへ値を書き込んだり、ダイヤルの値を取得したりできる。ただし、Addon Luaから任意の車載Luaグローバル変数やテーブルを直接取得するAPIはない。

したがって、Addonで同期できるのは、あらかじめ車両側に設計した入出力窓口を通る情報に限られる。全プレイヤーの車載Lua VMや「見えている世界」を丸ごと同期する汎用アドオンは、少なくとも一般公開されている範囲では確認できない。

## 10. 推奨設計

重要度に応じて状態を三分類すると設計しやすい。

### A. 常に現在入力から再計算できる値

例: 現在座標、現在速度、現在のキーパッド目標値。

Lua内へ永続保存せず、毎tick入力から計算する。これが最も安全である。

### B. 一時的に失ってもよい表示用状態

例: 画面ページ、点滅アニメーション、ローカルカーソル。

Lua内だけに置いてよい。ただし、プレイヤーごとに表示が異なることを許容する。

### C. 失うと制御結果が変わる重要状態

例: 発射時目標座標、追跡ID、誘導モード、積分器、フィルター状態。

次のいずれかを使う。

1. 車両ロジック／Compositeへループバックする
2. キーパッドやダイヤルなど、Addonから扱えるコンポーネントへ保持する
3. サーバーAddon側を正規状態とし、車両へ値を再注入する
4. 状態そのものではなく、同期済み入力と時刻情報から再構成できる設計にする

## 11. 座標保存の推奨パターン

概念的には、次のように「新規座標の有効信号」と「保存値の復元信号」を分ける。

```lua
bx, by, bz = 0, 0, 0

function onTick()
    -- 初回はループバックされた保存値を先に読む
    if input.getBool(32) then
        bx = input.getNumber(30)
        by = input.getNumber(31)
        bz = input.getNumber(32)
    end

    onTick = main
end

function main()
    -- Boolean 1が立ったtickだけ、新しい座標として確定する
    if input.getBool(1) then
        bx = input.getNumber(1)
        by = input.getNumber(2)
        bz = input.getNumber(3)
    end

    output.setNumber(30, bx)
    output.setNumber(31, by)
    output.setNumber(32, bz)
    output.setBool(32, true)

    -- 通常の利用先
    output.setNumber(1, bx)
    output.setNumber(2, by)
    output.setNumber(3, bz)
end
```

このコードは配線構成に合わせてチャンネルを調整する必要がある。また、単純な直結ループバックでは初期出力による上書き競合が起き得るため、Composite側でも「保存値が有効になるまで保持する」構成を用意するのが望ましい。

## 12. Dedicated Serverでの検証手順

同期問題は、表示と実際の物理挙動を分けて記録する。

1. プレイヤーAだけで参加し、座標を入力する
2. 入力元を0または無効状態へ戻す
3. Luaモニター、外部ダイヤル、実際の誘導出力を記録する
4. プレイヤーBを途中参加させる
5. AとBでモニター表示を比較する
6. 実際のミサイル軌道と命中地点をサーバー側観測を含めて比較する
7. Keep Activeの有無、車両から離れた場合、再接近した場合を試す
8. ループバック導入前後で同じ試験を繰り返す

テスト用に、次の値を外部ダイヤルやモニターへ表示すると原因を切り分けやすい。

- Lua起動後のtick数
- 初期化完了フラグ
- 保存中のX・Y・Z
- 新規入力の有効フラグ
- 現在の誘導モード
- ループバック読込成功フラグ
- 発射後経過tick

## 13. 最終的な判断

Stormworksの車載Luaでは、Lua内部状態を共有メモリとして扱ってはいけない。マルチプレイ対応が必要な装置では、**途中参加者が過去を知らなくても、現在の車両状態から必要な制御状態を復元できること**が重要になる。

最も堅い原則は次の三つである。

1. 現在入力から再計算できるものは保存しない
2. 保存が必要な重要値はLuaの外へループバックする
3. 表示上の差と、実際の物理・制御上の差を分けて検証する
